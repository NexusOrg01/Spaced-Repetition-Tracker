# Account-bound offline sync: staged implementation

## Scope of this PR

This PR adds and tests a local operation-queue primitive and ships it as a versioned, cache-safe script. It is deliberately **not wired into normal study saves or cloud uploads yet**. Activation is blocked until server-side idempotency and an isolated Supabase test environment can be verified. Activating a client-only queue against the existing snapshot table would create a second source of truth without proving that uncertain network responses can be retried safely.

This branch is based on PR #92 head `fix/account-choice-cancel-preserves-local-data` at `22ee3673c9980ba23c70b1504ddeb283582437e6`. PR #92 remains open/unmerged; this PR depends on it and targets that branch so its cancellation safeguards are included. After PR #92 merges, rebase this branch onto main and retarget the PR.

## Existing contract observed in code

- Main workspace and Study Hub state are stored in separate localStorage keys.
- Cloud persistence uses Supabase table `nexus_user_data`; writes compare `updated_at` and verify the resulting snapshot by reading it back.
- This is snapshot-level optimistic concurrency, not an operation-receipt/deduplication contract. A read-back after a lost response cannot prove exactly-once retry semantics.
- Preview/local origins currently block cloud sign-in to protect live cloud data.
- The available connected environment did not expose a verifiable isolated Supabase project or schema/RLS inspection. No Supabase migration was applied and no live configuration was changed.

## Queue primitive

`offline-sync-queue.js` records operation ID, explicit immutable owner namespace, entity ID/type, operation type, schema version, monotonic local sequence, base server version, payload, retry count, next-attempt time, and error code.

- The owner must be explicitly provided; it is never inferred from the currently active session.
- Pending reads filter by exact owner.
- Acknowledgement requires explicit server confirmation and a matching owner.
- Retries use bounded exponential backoff with jitter.
- Corrupt/unsupported queue data is surfaced and preserved rather than silently reset.
- Enqueue accepts companion localStorage entries so a future caller can commit workspace plus queue using the existing atomic localStorage transaction helper. This rollback pattern is not a substitute for IndexedDB/database transactions.
- The primitive does no network I/O and is not yet used by save paths in this PR; existing sync behavior remains unchanged.

## Required next stage before activation

1. Obtain an isolated Supabase development project and inspect exact `nexus_user_data` column types, constraints, grants, RLS policies, and ownership checks.
2. Add a versioned SQL migration with an operation receipt table and one transaction/RPC that validates `auth.uid()`, enforces ownership, deduplicates `(user_id, operation_id)`, checks expected revision, and commits receipt plus snapshot atomically. Do not emulate this with separate client requests.
3. Test repeated operation IDs, timeout-after-commit/retry, stale revision, concurrent writers, wrong owner, and RLS rejection on synthetic accounts.
4. Integrate queue commits with workspace/Study Hub saves and account switching. Sign-out pauses work but preserves owner-bound operations; resume only after verifying the same account.
5. Define event/revision rules for review events, FSRS, editable records, deletes, and Study Hub data before moving them off snapshot semantics.
6. Integrate backup/restore with recovery points and an explicit pending-queue policy. Restore cancellation must be a strict no-op; pre-restore operations must not silently upload into the restored workspace.
7. Only then enable automatic queue processing behind a feature flag and run the complete synthetic-account preview checklist.

## Backup compatibility and rollback

This PR does not change the backup schema or existing snapshot upload path. No queue is generated by normal study actions, so queue metadata is not added to user-facing backups yet. Before queue activation, backup migration must preserve/export pending operations or require an explicit pause/export/replace decision.

Rollback: revert/close the unmerged PR. No production state or Supabase schema was changed. The new script is inert unless a later change calls its API; no local keys are migrated or deleted. Service-worker cache v16 ensures the new helper is versioned with the app shell.
