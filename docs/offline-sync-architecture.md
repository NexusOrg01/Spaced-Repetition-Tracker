# Nexus account-bound offline sync

## Scope of this increment

Nexus currently stores one complete workspace snapshot per authenticated user in `public.nexus_user_data`. The client uses owner-only row-level security (RLS) and conditional updates against `updated_at`. The repository does not define a per-operation server table or server-side idempotency RPC. This PR therefore adds a durable, account-bound local outbox for complete workspace snapshots while retaining the existing cloud contract. It is a safe bridge, not a claim that event-level replication is complete.

## Local outbox and retry rules

- Each account also keeps a last-confirmed common workspace base plus the cloud revision it represents. If a same-account device has no queued edits and its local workspace still matches that base, Nexus simply loads the newer cloud workspace. If its local workspace differs from the base, Nexus queues that local snapshot and compares **Base**, **Local**, and **Cloud** instead of asking for a whole-workspace choice by default.
- Independent additions and independent field edits are combined automatically. Rows are matched by stable IDs. If both sides change the same field incompatibly, the local-device value is kept as a deterministic fallback and the alternative values are saved to a per-account conflict-recovery archive before the merged snapshot can be uploaded.
- A topic's FSRS card and associated review-scheduling fields are treated as one logical unit if both devices reviewed that topic concurrently. Nexus keeps one internally coherent schedule and archives the full alternative instead of mixing fields from two independent scheduler results. Independent topic notes/metadata still merge separately. Study Hub checklist selections merge as sets, so checking different items on two devices does not force a workspace choice.
- Deletion of a record is applied when the other side left that record unchanged. When deletion races with an edit, the edited record is preserved and the collision is archived rather than silently discarding the edit. The conflict archive can be downloaded from the cloud-sync area in Nexus for inspection.
- Automatic merge applies only when reconciling concurrent work for the same already-associated account. First sign-in with unassigned offline data and switching to a different account still require explicit data choices; this prevents personal work from leaking between accounts.

- Each pending snapshot records a stable operation ID, immutable owner user ID, workspace entity/type, schema version, monotonically increasing local sequence, base server revision, timestamps, and tracker + Study Hub payload.
- Workspace edits and outbox writes use the rollback-capable multi-key localStorage transaction helper. During automatic merge, tracker state, Study Hub state, account owner, new pending snapshot, normalized common base, and any conflict alternatives are committed together. If any part fails to persist, the old local workspace and queue are restored before in-memory state changes.
- Record arrays require stable IDs before normalization and merge. Missing or duplicate IDs fail closed instead of risking accidental record coalescing or loss. Cloud revision stamps are strictly newer than the revision being compared, including same-millisecond client writes.
- Pending snapshots are coalesced per owner because the current server stores a single whole-workspace snapshot. The latest snapshot replaces older unsent snapshots while retaining the original base server revision.
- Network restoration (`online`), page return (`pageshow`), and foregrounding (`visibilitychange`) re-check pending work. Transient connection/upload failures retry with exponential backoff from 1.5 seconds up to 5 minutes. Same-account compare-and-swap races trigger automatic reconnect/reconciliation; if the conflict read-back is interrupted by a network drop, reconnect is retried when connectivity returns. Retries pause for explicit data-choice requirements, sign-out, or an unsafe preview origin.
- On reconnect, every pending snapshot is checked even when the normalized tracker and Study Hub state appears equal to the cloud; this prevents metadata-only differences from leaving an outbox item stranded while the UI says “Synced.” A queued snapshot is uploaded automatically only when the observed remote revision still equals its stored base revision (or both remain absent for a first insert). A matching remote payload is acknowledged as already committed, including after a lost write response; a newer remote revision is treated as a conflict and is not overwritten automatically.
- Account A and Account B have independent queue entries. An upload requires the authenticated user ID and persisted workspace owner to match. Signing out does not remove the queue; switching accounts leaves the inactive account's pending snapshot parked.
- A snapshot is acknowledged only after read-back confirms the same tracker and Study Hub workspace content is remote. Normal writes verify the exact payload; recovery paths also recognize a semantically identical workspace when only export metadata differs. An ambiguous successful write advances the saved merge base before acknowledging the queue.
- If the remote revision differs from the queued base and the payload does not already match, same-account pending work first attempts a three-way merge against the last confirmed base. It retries a bounded number of times if the cloud changes during reconciliation. If reconciliation or its verified upload cannot complete, the queue is retained and sync pauses; it does not silently fall through to the account-choice dialog or overwrite the newer cloud version. A newer local snapshot created during an in-flight upload remains queued and is rebased only after the older snapshot is verified.
- If an explicit restore replaces a workspace with a pending snapshot, Nexus asks for confirmation and archives the previous snapshot in local recovery metadata before queuing the restored result.
- Invalid queue bytes are quarantined during the next workspace commit rather than silently overwritten. If the recovery slot is already occupied, the transaction fails closed and preserves the existing bytes.

## Backup compatibility

Portable JSON backups continue to include tracker state, validated FSRS cards embedded in topics, and Study Hub feature state. Backup metadata states that the account-bound queue itself is not portable; importing a queue into another browser/account would violate ownership isolation. Restoring a backup queues the resulting workspace under the currently persisted owner. A replace restore asks before archiving an existing pending snapshot. Legacy schema-3 backups continue through the existing migration path.

## Current IndexedDB entity projection (Phase 6.1)

The browser storage facade now maintains a separate owner-scoped entity projection for the active authenticated workspace. The projection is stored in the IndexedDB `workspaces`, `migrationMeta`, and `outbox` stores. It is not yet the source of truth for application startup, backup/restore, or cloud synchronization.

- Common tracker mutations pass stable-ID put/delete changes to the projection: topics, streams, subjects, exams, reviews, and bounded subject/stream cascades.
- Common Study Hub record mutations pass stable-ID changes for journal, papers, goals, and study logs. Tracker metadata and Study Hub metadata roots are refreshed with each projection update.
- Metadata-only changes send an empty record delta rather than rebuilding every entity row.
- Small multi-record changes use a bounded delta. Operations affecting more than 1,000 entity rows use a copy-on-write generation replacement so the client does not allocate an unbounded temporary change array.
- Whole-workspace replacement operations (restore/import, reset, undo, curriculum repair, and explicit repair flows) request a replacement generation.
- A replacement is staged in bounded batches. The previous active generation remains readable and its row-count/collection integrity metadata remains intact until the replacement is fully published. An interrupted or invalid replacement leaves the previous generation active; retry can build a new generation.
- Entity-change outbox reads and acknowledgements use owner-scoped sequence ranges and bounded pages. These local entity deltas are not currently sent to Supabase.

**Important limits:** `app-core.js` still serializes the full tracker and Study Hub compatibility snapshots on each save, commits them through the account-bound snapshot queue, and only then updates the entity projection. The local entity projection is therefore a recoverable mirror, not the authoritative application workspace. The cloud still stores and reconciles complete snapshots (chunked when large); the entity outbox is not a remote change log. This phase improves bounded entity maintenance and provides a migration foundation, but does not yet eliminate full-workspace serialization, full-snapshot queue writes, or full-snapshot cloud uploads.

## Validation and limitations

- Automated storage tests cover owner binding, generation replacement, an active generation remaining readable during a replacement, failure recovery, retries, metadata preservation after failed/invalid migration, duplicate/missing stable IDs, account isolation, atomic batches, bounded outbox sequence ranges, partial acknowledgements, legacy markers, and incremental row-count integrity.
- Large-workspace tests cover 77,144 topic records, more than 12,000 deletions, bounded rendering, merge yielding, and projection read/write fixtures. CI timings are regression measurements, not guarantees for all browsers or low-end devices.
- The existing conditional snapshot write and exact read-back verification remain the only server-side cloud retry protection. The retry policy is client-side: it improves eventual recovery while the page is open or returns to the foreground, but it is not a background sync worker and cannot run while the browser/app process is closed.
- No server-side per-record operation table, idempotency RPC, append-only event log, or delta compaction has been introduced. The entity outbox remains local-only. Remote synchronization is still whole-workspace snapshot synchronization with revision checks, merge and read-back verification.
- Server authorization still depends on the existing `nexus_user_data` schema and RLS policies. No production Supabase schema or policy has been changed. Staging-only schema work from the chunked snapshot phase remains isolated from production.
- Portable JSON backups continue to include tracker state, validated FSRS cards embedded in topics, and Study Hub feature state. The entity projection, account-bound snapshot queue, common merge base and conflict archive are not portable; importing a queue into another browser/account would violate ownership isolation. Restoring a backup queues the resulting workspace under the currently persisted owner.
- The current compatibility workspace and snapshot queue still have browser storage-quota limits. Entity projection maintenance does not yet remove the need for the complete snapshots or their storage capacity. A write failure must fail closed and preserve the prior workspace/queue; export a full JSON backup before continuing.
- The next migration phase must make entity records the authoritative local persistence path only after read/write transactions, account handoff, guest workspace adoption, offline recovery, undo/restore, FSRS review updates, curriculum tombstones, and backup compatibility are wired and tested together. The old snapshot must remain a recoverable fallback through the migration.
- Server-side incremental cloud synchronization is a separate follow-up: it needs atomic, owner-scoped publication, idempotent operation IDs, revision conflict handling, bounded reads, retention/compaction, and a snapshot recovery path. It must be tested against isolated staging before any production migration is considered.
- Do not test the preview against the production Supabase project. Do not merge until CI and the manual preview checklist pass.

## Account-switch display isolation

The account UI exposes the active Supabase user ID in the account element's title. A first-party guard compares that identity to the persisted workspace owner. If they differ, it covers and makes the app inert until the active account owns the loaded workspace. If a cloud load fails, the previous workspace remains stored but hidden; retrying reloads the active session, while signing out restores offline access to the previous workspace. This is a client-side display-safety barrier, not encryption of browser storage.
